# 知识库维护约定

## 组织与权威来源

- 根 docs 维护跨服务关系和项目约定；apps/<service>/docs 维护领域自己的知识。
- 源码和迁移描述当前实现；文档解释业务目的、约束和使用方法，发现不一致时明确修正。
- 功能文档描述“做什么”；领域文档描述“规则与边界”；实现文档描述“如何做”；测试文档描述“如何证明”。
- 相同契约只有一份正文，其他页面链接引用。移动文档时同步修复引用。
- 使用 Markdown，关系图和时序图使用 Mermaid 源码，便于随代码评审。

## 文件大小

每篇文档不得超过 2000 行，图表不计入上限。日常目标为几十至几百行。
优先按业务流程、模型或测试主题拆分，不建立不断追加的大杂烩文件。
统计时可排除 Mermaid fenced code block 和 Markdown 表格；若连图表在内都不超过 2000 行，则直接满足限制。

## 状态和可追溯性

- 已实现：指出具体代码入口或测试证据。
- 部分实现：分别写清领域、仓储、应用层和 HTTP 哪些已接通。
- 规划中：说明设计意图、待决策项和缺失能力，不声称已有接口或覆盖。
- 功能使用稳定编号，例如 SUB-001；测试场景用 TC-SUB-001-01。
- 测试文档记录前置条件、操作、预期结果、自动化函数链接和覆盖限制。
- 不把一次测试通过当成永久状态；测试数量仅作为有日期的验证记录。

## 更新检查清单

1. 规则变化：更新功能、领域、对应测试场景。
2. 表或事务变化：更新 ER 图、字段说明和时序图。
3. API 变化：更新契约、错误码及 API 测试映射。
4. 新增能力：更新服务知识库状态表与导航。
5. 校验相对链接、测试函数名称、Mermaid 语法与单文件行数。
6. 不在文档中存放密码、真实令牌或业务数据库连接。
